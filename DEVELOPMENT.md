# Development

See [README.md](./README.md) for setup and local run instructions. The project is managed as npm workspaces from the repository root.

Current implementation status: Phases 0–5. Registration, login, logout, cookie-backed session restoration, protected routes, owner-scoped scenario creation, asynchronous case generation, structured validation/retry, evidence generation, investigation/evidence views, viewed-evidence tracking, one-time accusation, backend scoring, and saved result reveal are implemented.

Run `npm test --workspace backend` for backend tests, `npm test --workspace frontend` for frontend tests, and `npm run build` for the production frontend build. Backend integration tests require a reachable MongoDB configured through `MONGODB_URI`.

Gemini calls happen on the backend only. The default text, image, and video model names are in `backend/.env.example`. Keep `GEMINI_API_KEY`, `JWT_SECRET`, and database credentials private. Generation retries are bounded by `GEMINI_MAX_ATTEMPTS`; text, image, and video timeouts have separate settings.

Generated bytes use local storage in `backend/storage/media/` unless `MEDIA_STORAGE_DIR` points to another local path. The directory must be private and persistent in production. Cloud storage can be added behind the media provider adapter without changing the evidence API.

CCTV evidence is playable only when the configured video provider returns actual video bytes. If video generation is missing or fails, the case labels the asset unavailable/failed and does not display a still frame as video.

The accusation is final. Scoring is backend-owned: 70 points for a correct suspect and up to 30 points for reviewing the proportion of available evidence records. The generated result snapshot is immutable after completion. Backend integration tests require a reachable MongoDB; Gemini and media providers are mocked in tests. No live Gemini calls are needed to run the test suites.

Evidence-plan validation keeps chat message timestamps within one day of the evidence timestamp, requires each CCTV timestamp to fall within 30 minutes of a related timeline event, and rejects clock times in evidence titles because the UI displays timestamps separately. CCTV recording time is stored from the validated evidence timestamp. Prompts also require suspect time/place statements and evidence titles/descriptions to agree with the case timeline; those free-text relationships cannot be fully checked by deterministic validators.
